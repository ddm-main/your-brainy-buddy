# JARVIS — Full Application Audit (2026-07-12)

Scope: complete audit of frontend, backend, Supabase, edge functions, business logic, security posture. Findings are grouped by severity. Fixes applied in this phase are marked ✅; the rest are queued for later phases and referenced by module.

---

## Blockers (must fix before shipping any Finance work)

| # | Area | Finding | Status |
|---|------|---------|--------|
| B1 | Edge fns ↔ DB | Every AI edge fn (`jarvis-chat`, `jarvis-tts`, `jarvis-transcribe`, `jarvis-vision`, `jarvis-vision-upload`) calls `increment_jarvis_usage(_user_id, _requests, _tokens, _endpoint)`, but the DB function was declared `(_user_id, _requests, _tokens)`. Every call logs `Could not find the function public.increment_jarvis_usage(...)` and quota fails open. | ✅ Fixed — DB fn now accepts `_endpoint`, `jarvis_usage_daily` keyed by `(user_id, day, endpoint)`, executor restricted to `service_role`. |
| B2 | Boot | `src/integrations/supabase/client.ts` read `VITE_SUPABASE_PUBLISHABLE_KEY` only; any environment injecting only the legacy `VITE_SUPABASE_ANON_KEY` initialised the client with `undefined` and never resolved `getSession()` → blank preview under `BootFallback`. | ✅ Fixed — now falls back to `VITE_SUPABASE_ANON_KEY` and logs a clear diagnostic when both are missing. |

## High

| # | Area | Finding |
|---|------|---------|
| H1 | Statements | `applyParsedStatementResult` in `finance-extract-core.ts` swallows parser failures; there is no `parse_error` column on `statements`, so failed statements sit at `parse_status = pending` forever. Users have no signal to retry. **Fix in Phase 1 next turn.** |
| H2 | Transactions | Parsing is regex-only (`_shared/finance-parsers.ts`). Unrecognised bank layouts silently produce zero rows. Needs regex-first / LLM-fallback pipeline with confidence persisted per row (the column already exists). |
| H3 | Loans | `Projects/finance/loans/…` UI has no amortization, no prepayment support, and does not auto-detect EMI debits against the linked account. `loanCalc.ts` covers the math but the UI never wires it end-to-end. |
| H4 | Cards | No `/finance/cards/:id` detail route. Utilization, statement history, per-card txn list, and "paid from which account" are not surfaced. |
| H5 | Subscriptions | No auto-detection. `subscriptions` table exists but is manual-only; recurring merchants in `transactions` are never grouped. |
| H6 | Reconciliation | `reconciliation_matches` table exists but has no UI. Duplicate/missing/suspicious txns are invisible. |
| H7 | Auth signup | `block_new_signups()` trigger hardcodes a single UUID. Fine for a personal OS; documented, not to be "fixed". |
| H8 | Password protection | Supabase Auth "Leaked Password Protection" is disabled (dashboard-only toggle). Enable at Auth → Providers → Password. Cannot fix from code. |

## Security posture summary

| Class | Status |
|-------|--------|
| RLS on user tables | Present on all 31 tables. Not re-audited row-by-row in this pass — queued for the security phase. |
| Service role key exposure | Not exposed. Server-only. Confirmed via `secrets--fetch_secrets`. |
| Storage RLS | Private buckets. Confirmed for `jarvis-vision`; `statement-pdfs` to be re-checked. |
| Statement password encryption | AES-256-GCM via `STATEMENT_ENC_SECRET`. Correct. |
| Function search_path | All security-definer fns set `search_path = public` explicitly. Correct. |
| Edge fn JWT verification | `requireUserId` validates via `SUPABASE_JWKS`. Correct. |
| Input validation | Present at edge-fn entry (size caps, MIME allowlists, SSRF guard on `jarvis-vision`). Adequate. |
| Leaked-password protection | **Disabled** — dashboard setting, needs user action. |
| Extension in `public` schema | Warned by linter (`pgcrypto` or similar). Cosmetic; low risk for personal OS. |
